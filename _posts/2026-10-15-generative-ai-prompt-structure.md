> **이번 글의 목표:** 프롬프트를 지시·맥락·입력·출력 형식으로 나누고, 각 블록이 하는 일을 구분해 빠진 조건을 스스로 검사한다.

먼저 결과부터 보자. `어텐션을 쉽게 설명해 줘.`라는 한 문장은 우리가 정한 네 블록 중 명시된 항목이 없어 충족률이 `0/4`, 즉 0%다. 같은 요청을 네 블록으로 나누면 `4/4`, 100%가 된다. Python으로 조립한 구조화 프롬프트의 길이는 147자다. 이 숫자는 답변 품질 점수가 아니라, **요청에 필요한 계약 항목을 빠뜨리지 않았는지** 확인한 결과다.

앞 글에서 [Transformer가 프롬프트의 토큰으로 다음 토큰 확률을 만드는 과정]({{ '/posts/generative-ai-transformer-inference/' | relative_url }})을 계산했다. 이번에는 모델 내부 계산 대신, 그 입력을 사람이 읽고 고칠 수 있는 구조로 만드는 데 집중한다.

## 1. 직관: 프롬프트는 정답 주문서가 아니라 작업 계약서다

모델은 사용자가 말하지 않은 독자, 근거 범위, 길이, 형식을 정확히 추측할 의무가 없다. “쉽게 설명해 줘”에는 무엇을 설명할지 외에는 기준이 거의 없다. 초보자용인지, 주어진 자료만 써야 하는지, 몇 문장으로 답할지도 열려 있다.

프롬프트를 네 블록으로 나누면 빈칸이 보인다.

- **지시:** 모델이 수행할 행동이다. 요약, 분류, 비교처럼 동사로 쓴다.
- **맥락:** 독자, 목적, 전제처럼 판단에 필요한 배경이다.
- **입력:** 실제로 처리할 자료나 질문이다.
- **출력 형식:** 언어, 항목 수, 길이, 표나 JSON 같은 결과의 모양이다.

네 블록은 모든 모델에 통하는 마법 공식이 아니다. 과제가 단순하면 짧은 한 문장으로 충분할 수 있고, 모델 종류에 따라 잘 맞는 표현도 달라진다. 다만 요청이 어긋났을 때 어느 부분이 비었는지 찾는 점검표로 쓸 수 있다.

## 2. 기호와 수식: 품질이 아니라 명시성을 센다

필수 블록 집합을 $R=\{\text{지시, 맥락, 입력, 출력 형식}\}$, 프롬프트에 실제로 있는 블록을 $P$라고 하자. 이번 실습의 충족률 $C$는 다음처럼 정의한다.

$$
C=\frac{|R\cap P|}{|R|}\times100
$$

모호한 요청은 네 제목이 하나도 없으므로 $C=0/4\times100=0\%$다. 구조화 요청은 네 제목을 모두 가지므로 $C=4/4\times100=100\%$다. 100%라고 해서 사실성이나 문장 품질이 보장되지는 않는다. 측정한 것은 오직 네 계약 항목의 존재 여부다. 실제 품질은 정답 예시와 평가 기준을 따로 마련해 반복 측정해야 한다.

## 3. 작은 예제: 한 문장을 네 블록으로 펼치기

같은 “어텐션 설명” 요청을 다음처럼 바꿔 보자.

```text
# 지시
다음 자료만 사용해 핵심 이유를 요약하세요.

# 맥락
독자는 생성형 AI를 처음 배우는 학생입니다.

# 입력
어텐션은 현재 위치가 앞선 토큰의 정보를 가중합하는 계산이다.

# 출력 형식
한국어 불릿 2개로 쓰고, 각 불릿은 20자 이내로 작성하세요.
```

지시는 행동을 고정하고, 맥락은 설명 수준을 정한다. 입력은 근거의 경계를 만들고, 출력 형식은 결과를 확인할 기준을 만든다. 특히 “짧게” 대신 “불릿 2개, 각 20자 이내”라고 쓰면 성공 여부를 사람이 직접 셀 수 있다.

Markdown 제목은 서로 다른 정보의 경계를 눈에 보이게 만든다. OpenAI의 현재 공식 문서는 Markdown 제목과 XML 태그로 프롬프트의 논리적 경계를 표시할 수 있다고 설명한다. Anthropic 공식 문서도 지시·맥락·입력이 섞일 때 각각을 일관된 XML 태그로 감싸면 구분이 선명해진다고 안내한다. 중요한 것은 특정 기호가 아니라 **블록의 이름과 경계를 일관되게 유지하는 것**이다.

## 4. 실행 가능한 Python 실습

다음 코드는 외부 API를 호출하지 않는다. 네 블록을 조립하고, 각 제목이 있는지만 결정적으로 검사한다.

```python
sections = {
    "지시": "다음 자료만 사용해 핵심 이유를 요약하세요.",
    "맥락": "독자는 생성형 AI를 처음 배우는 학생입니다.",
    "입력": "어텐션은 현재 위치가 앞선 토큰의 정보를 가중합하는 계산이다.",
    "출력 형식": "한국어 불릿 2개로 쓰고, 각 불릿은 20자 이내로 작성하세요.",
}


def build_prompt(items):
    return "\n\n".join(f"# {name}\n{text}" for name, text in items.items())


def missing_sections(prompt, names):
    return [name for name in names if f"# {name}" not in prompt]


vague_prompt = "어텐션을 쉽게 설명해 줘."
structured_prompt = build_prompt(sections)

for label, prompt in [
    ("모호한 요청", vague_prompt),
    ("구조화 요청", structured_prompt),
]:
    missing = missing_sections(prompt, sections)
    present = len(sections) - len(missing)
    coverage = 100 * present / len(sections)
    print(f"{label}: {present}/4 ({coverage:.0f}%), 누락={missing}")

print("구조화 프롬프트 길이:", len(structured_prompt))
```

실행 출력은 다음과 같다.

```text
모호한 요청: 0/4 (0%), 누락=['지시', '맥락', '입력', '출력 형식']
구조화 요청: 4/4 (100%), 누락=[]
구조화 프롬프트 길이: 147
```

## 5. 결과 해석: 구조는 생성 결과가 아니라 요구사항을 검증한다

검사기는 문장의 의미를 이해하지 않는다. 제목만 맞으면 100%를 주므로 잘못된 입력이나 서로 충돌하는 조건도 통과할 수 있다. 이 한계를 드러내는 것이 실습의 핵심이다. 프롬프트 구조는 품질 평가를 대신하지 않고, 평가 전에 **무엇을 요청했는지 고정하는 역할**을 한다.

2026년 10월 15일 확인한 OpenAI Responses API 문서에서는 고수준 행동 지침을 `instructions`, 실제 요청을 `input`으로 구분한다. 공식 문서는 `instructions`가 `input`보다 높은 우선순위를 가진다고 설명한다. API를 쓰지 않는 일반 대화에서도 지시와 입력 자료를 분리하는 습관은 같은 혼동을 줄여 준다.

출력 형식도 “예쁘게 써 줘”보다 검증 가능한 조건으로 바꾸는 편이 낫다. 다음 단원에서 다룰 JSON처럼 기계가 읽는 결과가 필요하다면 필드와 자료형까지 정해야 한다. 미리 감을 잡고 싶다면 [JSON 스키마로 도구 입력을 제한하는 글]({{ '/posts/ai-agent-tool-calling-json-schema/' | relative_url }})이 출력 규칙을 코드로 검사하는 방식을 보여 준다.

공식 문서들은 모델별 차이도 강조한다. OpenAI는 추론 모델에 간단하고 직접적인 요청, 분명한 구분자와 구체적인 성공 기준을 권한다. 따라서 프롬프트를 무조건 길게 만들거나 “단계별로 생각하라”는 문구를 습관적으로 붙이기보다, 필요한 블록만 채우고 실제 과제로 평가해야 한다.

## 6. 직접 바꿔 보는 연습

1. `출력 형식`을 “표 1개, 열은 개념·뜻·예시”로 바꾸고 길이와 충족률을 다시 확인한다.
2. `맥락` 블록을 삭제해 충족률이 75%가 되는지 확인한다.
3. 제목은 모두 두되 입력을 빈 문자열로 바꿔 보자. 현재 검사기가 놓치는 문제를 찾고, 빈 값도 누락으로 처리하도록 함수를 고친다.

## 핵심 요약

- 프롬프트의 지시는 행동, 맥락은 판단 배경, 입력은 처리 자료, 출력 형식은 결과의 모양을 맡는다.
- 네 블록은 답변 품질을 보장하는 공식이 아니라 누락된 요구사항을 찾는 점검표다.
- 제목이나 XML 같은 구분자는 지시와 자료의 경계를 분명하게 만든다.
- 실제 품질은 모델 출력과 평가 기준으로 따로 측정해야 한다.
