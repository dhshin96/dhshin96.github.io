> **이번 글의 목표:** 바뀌는 지식과 반복되는 행동을 구분하고, 평가 결과와 예제 데이터가 있을 때 파인튜닝을 검토하는 선택 순서를 세운다.

먼저 결과부터 보자. 네 요구를 같은 규칙에 넣자 최신 정책 질의는 `RAG`, 이미 90% 통과한 JSON 보고서는 `프롬프트 유지`, 통과율 62%인 반복 분류는 `파인튜닝 검토`, 좋은 예제가 20개뿐인 말투 통일은 `프롬프트+데이터`로 나뉘었다. **파인튜닝은 모든 부족함을 해결하는 첫 단계가 아니라, 지식 문제가 아니고 프롬프트만으로 남은 행동 격차를 측정했으며 대표 예제도 준비됐을 때의 후보**다.

앞 글의 [검색 성공과 답변 충실성을 나눠 잰 평가 방법]({{ '/posts/generative-ai-rag-quality-evaluation/' | relative_url }})을 먼저 보면 여기서 쓰는 `prompt_pass`가 왜 감이 아니라 평가표에서 나와야 하는지 이해하기 쉽다.

## 1. 직관: 세 방법은 서로 다른 곳을 바꾼다

프롬프트는 한 번의 요청에 들어가는 **지시와 예시**를 바꾼다. 규칙을 더 명확히 쓰거나 정답 예시 몇 개를 보여 주는 방식이다. [지시·맥락·입력·형식을 나눈 프롬프트 구조]({{ '/posts/generative-ai-prompt-structure/' | relative_url }})만으로 원하는 결과가 나온다면 학습을 추가할 이유가 없다.

RAG는 모델 가중치를 바꾸지 않고 답변 시점에 볼 **외부 근거**를 바꾼다. 사규, 가격표, 매뉴얼처럼 갱신되는 정보가 필요하다면 [문서를 검색해 생성 입력에 붙이는 RAG 흐름]({{ '/posts/generative-ai-rag-retrieval-grounding/' | relative_url }})이 먼저다. 문서가 바뀔 때 색인을 갱신할 수 있고, 어떤 근거를 사용했는지도 남길 수 있다.

파인튜닝은 입력·정답 예시 쌍으로 학습해 모델의 **반복 행동**을 조정한다. 특정 분류 기준, 일정한 말투, 복잡한 지시 따르기가 프롬프트만으로 계속 흔들릴 때 검토한다. 그러나 학습 데이터 제작, 학습 실행, 별도 평가와 모델 수명 관리가 추가된다. 새 사실을 자주 넣는 저장소처럼 쓰면 사실이 바뀔 때마다 다시 학습해야 하므로 출발점이 잘못된다.

## 2. 기호와 수식: 파인튜닝 후보 조건을 네 칸으로 나눈다

요구 하나에 대해 다음 값을 0 또는 1로 두자.

- $K$: 답에 최신·외부 지식이 필요하다.
- $B$: 고치려는 대상이 여러 입력에서 반복되는 행동이다.
- $G$: 프롬프트 평가 통과율이 목표보다 낮다.
- $D$: 대표성이 있고 검토된 입력·정답 예제가 충분하다.

파인튜닝 후보 $F$를 다음처럼 단순화할 수 있다.

$$
F=(1-K)\land B\land G\land D
$$

$K=1$이면 먼저 RAG를 검토한다. $K=0$이어도 $G=0$이면 현재 프롬프트가 이미 목표를 만족하므로 유지한다. 나머지에서 $B$와 $D$가 모두 1일 때만 $F=1$이다. 이것은 보편 법칙이나 성능 보장이 아니라, 비싼 학습을 시작하기 전에 빠진 근거가 없는지 확인하는 입문용 안전장치다.

## 3. 작은 손계산: 네 요구를 같은 순서로 판정한다

목표 통과율을 예시로 80%라 하자. 최신 정책 질의는 $K=1$이므로 다른 값과 상관없이 RAG다. JSON 보고서는 프롬프트 통과율이 90%라 $G=0$이고, 그대로 유지한다.

의도 분류는 지식 갱신이 필요 없고 반복 행동이며, 통과율 62%라 격차가 있다. 검토된 예제가 80개이므로 $(1-K)BGD=1$이 되어 파인튜닝 후보다. 말투 통일은 같은 행동 문제지만 예제가 20개뿐이라고 가정한다. 여기서는 $D=0$으로 두므로 먼저 프롬프트를 다듬고 다양한 예제를 더 모은다. 80%와 50개 기준은 아래 실습을 결정적으로 만들기 위한 값이며, 실제 기준은 과제·위험·데이터 품질에 맞춰 정해야 한다.

## 4. 실행 가능한 Python 실습

아래 코드는 외부 API나 패키지를 쓰지 않는다. `changing_knowledge`를 가장 먼저 검사하고, 그다음 프롬프트 기준과 데이터 준비 상태를 본다.

```python
cases = [
    {"name": "최신 정책 질의", "changing_knowledge": True,
     "stable_behavior": False, "examples": 0, "prompt_pass": 0.55},
    {"name": "JSON 보고서", "changing_knowledge": False,
     "stable_behavior": True, "examples": 15, "prompt_pass": 0.90},
    {"name": "의도 분류", "changing_knowledge": False,
     "stable_behavior": True, "examples": 80, "prompt_pass": 0.62},
    {"name": "말투 통일", "changing_knowledge": False,
     "stable_behavior": True, "examples": 20, "prompt_pass": 0.65},
]

TARGET_PASS = 0.80
MIN_EXAMPLES = 50  # 이 실습의 예시 기준

def choose(case):
    if case["changing_knowledge"]:
        return "RAG"
    if case["prompt_pass"] >= TARGET_PASS:
        return "프롬프트 유지"
    if case["stable_behavior"] and case["examples"] >= MIN_EXAMPLES:
        return "파인튜닝 검토"
    return "프롬프트+데이터"

for case in cases:
    print(f'{case["name"]}: {choose(case)}')
```

실행 출력은 다음과 같다.

```text
최신 정책 질의: RAG
JSON 보고서: 프롬프트 유지
의도 분류: 파인튜닝 검토
말투 통일: 프롬프트+데이터
```

## 5. 결과 해석: 후보가 됐다고 바로 학습하지 않는다

OpenAI의 모델 최적화 문서는 먼저 평가 기준을 만들고, 프롬프트에 지시·맥락·예시를 제공한 뒤 일부 과제에서 파인튜닝을 검토하고 다시 평가하는 순서를 제시한다. 지도 파인튜닝 안내도 기본 모델보다 좋아졌는지 판별할 평가를 먼저 만들라고 강조하며, 잘 만든 시범 예제 50개로 시작해 결과를 평가하는 방법을 안내한다. 따라서 코드의 50은 이 안내를 반영한 출발값일 뿐, 예제 수만 채우면 학습할 수 있다는 뜻이 아니다.

학습 예제와 최종 평가 예제도 나눠야 한다. 같은 문장을 양쪽에 넣으면 모델이 처음 보는 입력에도 잘 작동하는지 확인할 수 없다. 먼저 실제 입력 범위를 대표하는 평가표를 고정하고, 학습에는 다른 예제를 사용한다. 파인튜닝 뒤에는 전체 평균뿐 아니라 드문 입력, 길이가 긴 입력, 잘못 거절하기 쉬운 입력을 따로 비교해야 한다. 개선된 항목과 나빠진 항목을 함께 보지 않으면 한 행동을 고치며 다른 행동을 망친 변화를 놓친다.

RAG와 파인튜닝은 서로 배타적이지 않다. 바뀌는 정책은 검색으로 공급하면서, 검색된 근거를 항상 정해진 분류표나 말투로 요약하는 반복 행동만 학습할 수 있다. 이 경우에도 검색 적중률과 행동 통과율을 따로 재야 한다. RAG가 틀린 문서를 가져온 실패를 파인튜닝 데이터로 덮으려 하면 원인과 처방이 다시 섞인다.

또한 2026년 11월 22일 확인한 OpenAI 공식 문서는 해당 파인튜닝 플랫폼을 축소 중이며 신규 사용자는 접근할 수 없다고 명시한다. 지원 모델과 API는 공급자와 시점에 따라 달라지므로 이번 실습은 호출 결과를 만들지 않았다. 개념적으로는 자체 모델의 전체 가중치를 갱신할 수도 있고, LoRA처럼 기존 가중치를 고정한 채 작은 저랭크 행렬만 학습할 수도 있다. LoRA 논문은 $\Delta W=BA$로 업데이트를 표현해 학습할 매개변수를 줄이지만, 데이터와 평가가 필요하다는 선택 기준까지 없애지는 않는다.

## 6. 직접 바꿔 보는 연습

1. `TARGET_PASS`를 `0.95`로 올려 어떤 요구의 선택이 바뀌는지 확인한다.
2. 말투 통일의 `examples`를 60으로 바꾸고 왜 파인튜닝 후보가 되는지 네 조건으로 설명한다.
3. `stable_behavior`가 `False`인 일회성 요약 요구를 추가해 결과가 `프롬프트+데이터`인지 확인한다.
4. 실제 과제에서는 예제 수 대신 중복 제거, 오류 검토, 입력 범위 대표성을 확인하는 `data_ready` 값을 직접 만든다.

## 핵심 요약

- 프롬프트는 현재 요청의 지시·예시를, RAG는 답변 시점의 외부 근거를, 파인튜닝은 반복되는 모델 행동을 바꾼다.
- 최신·변경 가능 지식이 필요하면 RAG를 먼저 검토하고, 프롬프트 평가가 이미 목표를 넘으면 그대로 유지한다.
- 파인튜닝은 측정된 행동 격차, 반복 과제, 검토된 대표 데이터가 함께 있을 때만 후보가 된다.
- 후보를 골랐어도 기본 모델과 같은 테스트 데이터로 비교 평가해야 실제 개선을 말할 수 있다.
